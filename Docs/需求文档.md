引擎：Unity 2022.3.52f1｜形态：竖屏 2D 休闲游戏（编辑器鼠标 / Android 触摸）｜版本 v1.1

### 2026-10-24 HUD 与提示收敛（用户确认，FR-08A / FR-21D）

- FR-08A：左上统一深蓝半透明面板，默认保护／主钩／深度三行；分支已激活或仍有分支鱼获时显示第四行，展开不移动前三行。图标、中文标签、右对齐数值各占独立列，数值采用真实 Model；保护改用现有厚泡膜水泡，与钩上保护泡对应，次数耗尽或阶段不可用时变暗，扣减时短暂亮一次。
- FR-08B：深度连续读数不弹跳；捕获和保护数量变化采用约 0.14 秒、最大 1.055 倍的轻微反馈，暂停冻结，重开清理。左上四行标签与数值采用 Bold 样式，保持现有字号、列间距和最长数值可读性。保留右上双竖条暂停键，视觉 60×60、触摸区 78×78，静态 HUD 不拦截拖动；覆盖 450×800/975/1050 与 1200×2670 及模拟安全区。
- FR-21D（2026-10-26 随操控模式更新）：保留安全区底端的一行淡色提示，不增加独立收线说明块。手机按当前有效模式说明倾斜或拖动选路，以及任意非按钮区域点按／按住收线；电脑说明鼠标拖动／空格收线。下潜开局仍使用同一底端提示节点；满载、暂停、出水与结算隐藏。教学第一页和第三页随有效手机模式更新，保留绿区与鱼标示意、按住上抬／松开下落、稳固恢复和失稳先逃贵鱼说明，不要求左右手分区；三页教学与首次开始流程不变。
- FR-17A / FR-29B：展示名统一为 Fishrise，中文副标题保留冰湖垂钓。临近水面才满载不改变深度到构图的映射；按本局可达最高上收速度提前准备镜头，保留 2.3 秒自然出水与无跳过按钮。
- FR-12A：结算鱼种仍采用可滚动两列卡片，保留星级、数量、单位收益、主钩／分支来源和总收益。移除鱼身后的矩形底板，放大鱼图；卡片改为圆角蓝色渐层、柔和聚光与细亮边，数量采用橙色小标签。进入动画保持鱼图比例，不再横向压扁展开；空鱼获、七鱼种滚动与重开清理保持。

### 2026-10-24 Fishrise 出水演出（用户要求，FR-29）

- FR-29B 补充（2026-10-25）：收钩演出时分散钩连接线位于主钩金属后方，不得横盖主钩；保留已验收的收拢路径、连接端点、受光与穿洞空间。

- FR-29A 连贯动作：用当前挂鱼姿态衔接破水，主钩视觉副本带鱼升至冰面上方；钩顶以当前弯曲后的竿尖为上限，保留至少 0.45 世界单位的竖向距离，避免钩越过竿尖、鱼线反折。分散钩临近水面时真实收拢到洞口，判定跟随实际钩位，挂鱼改为窄幅挂放；穿洞需检查完整钩体、鱼身旋转外框及连线，不能只检查中心点。进入出水演出后禁用分散钩判定，继续复用原视图完成穿洞，完整离开冰沿后才向两侧展开；中央和左右极限回收、满载加速及较大时间步均应通过。鱼分批脱钩后独立沿弧线飞过竿尖并落向现有木桶，脱钩瞬间记录起飞姿态，不再随竿尖改变。分支释放比主钩晚约 0.3 秒，保留来源区别。空中演出不能移动实际主钩的判定位置、改变捕获记录或重复提交收益。
- FR-29B 受光与镜头：出水鱼使用场景网格，复用冰面已有天空与灯笼 Light2D；共享变形材质用程序曲面法线近似体积，鱼尾绕嘴部方向摆动。镜头在最后一段上收时提前平滑准备构图，近水面约 1.5 米前完成过渡；人物与背景构图同步准备，约束钩仍处于可见区域，临近水面逐渐收掉满载抖动。出水甩钩阶段不再缩放或快速平移，只保留微弱破水冲击；最终水平半宽约 4.7，允许收窄两侧远景，左右前景冰层仍保留可见厚度；冰面水线约位于距底部 38%，人物近景放大至原场景的 1.45 倍，屏幕宽度约 31%；天空采用连续、低对比的阴云衔接山景与画面顶部，避免重复云图。脱钩鱼群向人物上方抛起，人物和鱼获形成分开的轮廓，鱼竿蓄力弯曲并回弹，鱼线端点连接空中钩顶。多比例下鱼获保持可见并避开标题，结算保留构图，新局恢复。动画总时长仍为 2.3 秒。
- FR-29C 奖励与生命周期：金额延后出现、取消逐条黑底卡片，在三条显示通道中错峰，使用金币图标配金色分数，不附带来源；默认总演出仍为 2.3 秒，上限 2.5 秒，自动进入结算，不显示跳过按钮（本次用户修订）。后台冻结，结算／重开立即清理鱼、钩、水滴和文字，不残留副本或重复结算。出水仍不开放玩家手动暂停；旧提前结束接口仅保留内部兼容与清理回归。
- FR-29D 资源：先复用既有鱼、钩、木桶和程序水滴，无新增图片依赖；保留共享变形材质，并增加连续天空、浅水冰体和浅水折射三份共享材质及 shader。圆润卡通人物、七鱼种和冰面的规格与生成提示词见 `Docs/Fishrise出水资源提示词.md`，先做蓝色条纹鱼与提竿人物样张，待用户生成和对齐后再接入。网格形变和弧线属于受控动画，不声称实现鱼类／人物三维模型、真实刚体绳索、鱼体软体或 GPU 性能优化；原 demo 的实时／预渲染技术路线尚无法从录屏确认。
- FR-29E 场景尺度与浅水层次：近景人物、气象杆、木桶、木台与灯笼应具有一致尺度，气象杆约为人物高度的 1.6～2 倍，桶约为一半，灯笼约为 1/3～2/5；灯笼落在木台实际承托面，光源和接地阴影跟随。按用户 2026-10-25 最新确认改为正面剖视：水平雪沿、直落冰洞，人物鞋底、凳脚、木台脚和桶底贴地；洞口适当加宽，雪唇与内壁以小圆角、受光亮边和内侧暗部表现厚度，保留剖视构图。远山降对比、增加冷色空气透视，山底与雪沿衔接，不露空隙。冰面下保留连续冰体、错落冰柱、浅水焦散及画面折射，中央开口清晰，鱼与钩仍可辨认；装饰不改变碰撞和捕获。出水飘字由金币图标与得分组成，不附带“分支”等来源。环境运动受暂停控制，重开不堆叠资源，多种竖屏不得裁掉道具。

- FR-29A / FR-29E 补充（2026-10-25）：满载加速下也要有可读的分散钩收拢过程；按最高可能速度提前规划，临水面才满载不得提前回收水下分散钩。相机联合检查钩与挂鱼的完整下沿，保证上收时留在视口、出水甩钩阶段保持稳定。冰洞内壁加入不对称凹槽和小型冰台，以受光面补厚度；中央最窄通道保持 1.5 世界单位。

### 2026-10-21 交互收线扩展（用户确认，分阶段实施）

- FR-21A 操作与手感（2026-10-26 用户修订）：设置中提供“拖动”和“倾斜”两种模式，默认保留拖动；菜单与暂停设置共用并立即保存模式和灵敏度。取消左右／右下操作分区，UI 起始触点仍排除。电脑保留鼠标拖动＋空格，不改控条难度、稳固度、逃鱼及满载规则。
- 拖动模式：有效收线阶段以约 12 逻辑像素（按 720 参考宽度换算）的位移阈值优先识别拖动；未越阈值的短点在抬起时触发一次控条微调，原地按住约 0.1 秒后持续收线。按住转拖动后，同一手指停止收线直到松开；可用单指交替操作，也可由另一根手指在任意空白处辅助收线。2026-10-26 手感修订：相对拖动位移增益提高为 1.25 倍，最大横移速度与湖边界不变，绝对贴点模式仍保持指钩对应；不降低手势识别阈值，避免按住收线更易被误判为拖动。不丢失物理步之间的短点，不把取消／丢失触点当成点按，不按触点数组顺序抢占。
- 倾斜模式：以自然握姿为中立，倒计时自动校准约 0.35 秒，暂停设置可重新校准；用重力／姿态的左右倾斜映射横移速度，不累计原始角速度定位。2026-10-26 手感修订：死区由 2.5° 降为 1°，标准满幅由 15° 降为 12°，滤波时间常数由 0.06 秒缩短为 0.04 秒；保留 0.75／1／1.5 倍灵敏度，1.5 倍约 8.33° 达最大速度。回正停在当前位置，不自动回中，保留原限速和湖边界。任何已接纳的非按钮触点立即按住收线，移动手指不打断持有。
- 生命周期与能力：暂停、后台、切换模式、阶段变化及重开清理手势和收线残留；倒计时可采样校准，但倒计时／出水／结算不允许体感移动鱼钩。校准中不移动，不持久保存中立姿态。无可用陀螺仪及加速度计时明确提示并使用拖动，仍保留玩家选择的倾斜偏好；不迁移输入后端，保持 Legacy API 与 Both 配置。
- FR-21B 控条与速度：鱼钩左上方显示固定逻辑尺寸控条，不拦截触摸；避开安全区、顶部 HUD 与下方拇指区，抵消镜头抖动。仅上收且有鱼时显示；操作质量控制约 2–6 米/秒的缓冲上收，空钩仍按 6.5 米/秒自动返回。启用新玩法时，本扩展覆盖 FR-02/05 的满载 ×5 自动加速，满载容量／捕获分配保持。
- FR-21C 数量难度：当前挂鱼总数包含主钩＋分支，按当前总容量归一化；绿区高度由 42% 线性插值到 28%，数量变化约 0.6 秒缓动。首版鱼标最高速度与稳固度增减速度固定，避免多项难度叠加；所有比例与速度是初始调参值。
- FR-22A 价值优先逃鱼：稳固值归零，每次从全部留存鱼获中逃走一条，金币单价高者优先，同金币比较贝壳单价，完全同价按原提交顺序。使用捕获记录的本局价值快照，不给两种货币虚构兑换率。数量继续决定绿区宽度，价值决定先逃谁；控条显示下一条风险鱼种及图标。
- FR-22B 记录与恢复：逃鱼立即移除留存记录，原来源钩容量、收益、结算同步更新；保持本局已捕获身份，禁止延迟接触重复钓回。原来源钩的剩余挂点紧凑排列，其他钩保持；全部逃光后自动空钩返回。每次损失后稳固值恢复 45%，给予 0.8 秒失稳缓冲，避免连续瞬间清空。
- FR-22C 能力宽限：成功展开分散鱼钩后给予 0.8 秒缓冲，重复/失败命令不刷新；缓冲仅阻止失配扣稳固值，控条、鱼标和上收照常，计时随暂停冻结，重开清零。稳固增长/下降、损失后恢复值与两类宽限均在 FishingConfig 可调。
- 第一检查点为无逃鱼的基础原型；第二检查点接入 FR-22A/B/C。`FishingConfig.enableReeling` 默认启用，关闭时保留旧玩法对照；旧规则测试显式关闭、测试后恢复原值，新模式有独立场景验证。Editor 自动测试、实际键鼠、手机双指和 APK 分别验收。

## 3. 玩法与流程设计

### 3.1 状态机

| 状态 | 进入条件 | 玩家可做 | 离开条件 |
| --- | --- | --- | --- |
| Menu 起始页 | 应用启动，或结算与暂停菜单点“退出” | 开始游戏、教学、退出 | 点“开始游戏”进入 Countdown（首次先进入 Tutorial）；点“教学”进入 Tutorial；点“退出”关闭应用 |
| Tutorial 教学 | 首次点“开始游戏”自动进入，或在起始页点“教学” | 翻页、关闭 | 首次开始则关闭后进入 Countdown；从起始页点“教学”进入则关闭后回到 Menu |
| Countdown 倒计时 | 点“开始游戏”（首次先教学）或重开 | 无 | 3 秒结束进入 Diving |
| Diving 下潜 | 倒计时结束 | 左右移动 | 到最大深度进入 BottomHold；无保护触碰进入 Ascending |
| BottomHold 底部停留 | 到达最大深度 | 左右移动 | 停留 0.18 秒进入 Ascending，随后 0.35 秒缓起速 |
| Ascending 上收 | 底部停留结束或提前上收 | 左右移动，触碰鱼头捕获 | 到达水面进入 Surfacing |
| Surfacing 出水演出 | 鱼钩到水面 | 自动播放，无跳过按钮 | 演出完进入 Result |
| Result 结算 | 演出完成 | 再来一局、退出 | 再来一局回到 Countdown；退出回到 Menu |
| Paused 暂停（覆盖层） | 点暂停，仅 Diving、BottomHold、Ascending 可用 | 继续、重开、退出 | 继续回到暂停前状态；退出回到 Menu |

满载不是独立流程状态，`IsFull` 由主钩捕获数是否达到主容量派生，分支捕获数不参与。底部区若已抓满，停止主钩捕获，但仍按原流程完成下潜与底部停留；仅在 Ascending 中应用满载速度倍率与红色钩灯。暂停期间物理、计时、动画、音效全部停止，恢复后从原状态继续。

### 3.2 核心规则

| 编号 | 规则 | 标注 |
| --- | --- | --- |
| R1 | 下潜自动向下，玩家只控制横向位置 | 确认 |
| R2 | 下潜期且未进入底部区时，新接触任意可捕获鱼（含小鱼）的鱼头：有保护则保护 −1，该鱼不被捕获，主钩获得 1 秒无敌；无保护且不在无敌期则捕获该鱼并立即转入上收。同一次持续重叠只判定一次，分离后再次接触才重新判定 | 原版含义为推断；接触与无敌处理为设计约定 |
| R3 | 进入底部区及 BottomHold 后，保护与保护产生的无敌均失效；主钩未满时触碰即捕获，但不触发提前上收；到达最大深度停留后上收 | 现象为依据；捕获与状态处理为设计约定 |
| R4 | 上收期主钩未满时，触碰鱼头即捕获，主钩捕获数 +1，鱼挂到主钩上；分支钩按 R10 与第 8.4 节独立判定 | 基础玩法为确认；多钩分配为设计约定 |
| R5 | 主钩捕获数达到主容量即满载，满载事件每局只发一次；上收期速度倍率生效、主钩灯变红，主钩不再捕获，分支钩仍可按自身容量捕获一星鱼 | 基础满载表现为确认；底部与分支处理为设计约定 |
| R6 | 鱼钩回到水面后进入出水演出，再进入结算 | 确认 |
| R7 | 收益等于主钩与分支全部捕获记录的价值之和；结算每个鱼种只显示一张卡片，列出总数量及“主钩 ×N / 分支 ×M”，有分支捕获时显示“含分支”角标 | 基础结算为确认；来源明细为设计约定 |
| R8 | 重开时重新创建本局数据与全部鱼，不复用上一局任何状态 | 要求 |
| R9 | 下潜期可释放声呐：驱散半径内的小鱼，受惊期内这些小鱼的判定区关闭，不扣保护也不触发收钩（见 8.5.1） | 新增，已确认 |
| R10 | 上收期可展开分散鱼钩：分支钩可捕获所有一星鱼，不占主容量（见 8.4） | 用户修订，已确认 |

### 3.3 边界情况约定

| 情形 | 处理 |
| --- | --- |
| 同一物理步碰到多条鱼（下潜有保护） | 只处理最近的一次有效新接触并消耗 1 次保护；本步其余新接触按无敌处理，持续重叠不补扣 |
| 同一物理步碰到多条鱼（下潜无保护） | 只取最近的一条捕获并转上收，本步不追加捕获其余鱼；下一物理步仍接触或发生新接触的鱼按上收规则处理 |
| 同一物理步碰到多条鱼（上收） | 先分配有余量的分支钩，再分配主钩；每轮按距离、鱼实例 ID、钩 ID 排序，直到对应容量用尽。完整顺序见 3.4 节 |
| 同一次接触持续多个物理步 | 保护最多扣 1 次；无敌结束仍重叠也不再扣。鱼钩与该鱼完全分离后再次进入，才是新接触；捕获后立即关闭判定区 |
| 保护无敌期内发生新接触 | 不扣保护、不捕获，并记录该接触已进入；无敌结束不追补，必须分离后再进入才重新判定。无敌仅在 Diving 且未进入底部区时有效 |
| 进入底部区或从下潜转为上收 | 清除保护无敌并重置接触阶段记录；新阶段首个物理步将仍重叠的鱼纳入候选，已捕获去重记录保留 |
| 暂停中 | 不处理任何碰撞与输入 |
| 到达最大深度的同一物理步又发生触碰 | 深度先限制到最大深度，按底部区规则结算接触，再切换到 BottomHold；已经满载也不跳过底部停留 |

### 3.4 接触收集与多钩统一裁决

1. 以固定物理步为裁决单位，同一物理步内的候选视为同时接触。触发回调与扫掠检测只收集候选，不直接扣保护或登记捕获；同一步同一钩与同一鱼的重复报告合并。
2. Unity 适配层在本步移动与检测完成后，提交完整候选批次。每条候选携带局 ID、物理步序号、来源钩 ID、鱼的本局实例 ID、鱼种 ID 与距离平方；距离取本步钩头路径到鱼头判定中心的最近距离。规则层不接收 Collider、GameObject 或其他 Unity 对象。
3. 下潜按第 3.3 节处理。上收先处理所有已展开且有余量的分支钩候选，只允许一星且可捕获的鱼，不区分体型；按距离、鱼实例 ID、钩 ID 升序裁决。一个分支满时仍可尝试另一个同样接触该鱼的分支。
4. 再处理未被分支捕获的主钩候选，按同样顺序裁决，直到主钩满载。分支已满或无法接收时，接触主钩的鱼仍可占用主容量；同一物理步内分支优先，跨步则已捕获结果保持不变。
5. 分配期间维护本批次的临时剩余容量与已分配鱼集合，每分配一条立即占用对应余量，避免提交前超限或重复分配。分配完成后由 FishingFlowController 统一提交到 RunModel，登记全局捕获去重集合后发事件。BranchHookController 提供分支资格和容量判断，不在回调中单独登记收益，也不依赖 View 回调更新容量。
6. 暂停时不提交批次；重开或退出时清空候选与接触记录，丢弃旧局 ID 的迟到报告。不同回调顺序必须产生相同结果。

## 4. 功能需求

优先级：**P0** 必做，缺它玩法不成立；**P1** 应做，明显提升完成度；**P2** 加分。

### 5.3 运行时数据（RunModel）

- 状态：局 ID、当前流程状态、是否暂停；`IsFull` 由主钩捕获数达到主钩容量派生。
- 数值：当前深度、最大深度、剩余保护、无敌截止时间、主钩容量；`MainCaptureCount`、`BranchCaptureCount` 与 `TotalCaptureCount` 分别表示主钩、分支合计和全部捕获数。
- 记录：`List<CaptureRecord>` 是全部捕获的唯一记录源，每条含鱼种 ID、鱼的本局实例 ID、捕获来源（Main / Branch）、来源钩 ID、捕获深度与游戏时间。对象池再次启用的鱼必须分配新的本局实例 ID，不把池对象 ID 当作捕获身份。
- 派生：主钩数与分支数从记录按来源统计，总捕获数＝两者之和＝记录条数；金币与贝壳总额覆盖所有来源。按鱼种聚合时同时保留总数量、主钩数量和分支数量。
- 分支状态：BranchHookModel 保存展开状态与各分支容量；每钩已用数量按 RunModel 的记录和来源钩 ID 统计，不另存一份捕获清单。
- 原则：配置快照只读；**每局新建** RunModel；Model 是纯 C# 类，不引用任何 Unity 资源或场景组件。原始 ScriptableObject 配置到规则数据的转换见 6.1。

### 5.4 数据结构选型

| 结构 | 用途 | 理由 |
| --- | --- | --- |
| `List<CaptureRecord>` | 本局捕获记录 | 保持顺序，出水演出按序弹出 |
| `Dictionary<string, FishSummary>` | 结算按鱼种聚合，保存总数量与主钩、分支数量 | 平均 O(1) 累加与查询，来源明细不丢失 |
| `HashSet<int>` | 本局已经捕获的鱼实例 ID | 所有钩共用，防重复捕获；重开清空，不用于永久屏蔽扣过保护的鱼 |
| 按钩 ID 与鱼实例 ID 组成的接触集合 | 上一物理步仍重叠的接触及本次进入记录 | 区分持续重叠与分离后再次进入，独立于捕获去重集合 |
| `Queue` / `Stack` | 对象池 | 取用与归还简单 |
| `Dictionary<RunState, IState>` | 状态机 | 查表切换，免去大段分支 |
| 按物理步归集的候选列表 | 多接触与多钩裁决 | 先分支后主钩，每轮按距离、鱼实例 ID、钩 ID 排序，结果不依赖回调顺序 |
| `event` / `Action` | 观察者通知 | 解耦规则与表现 |

## 6. 架构设计

### 6.1 分层与数据流

| 层 | 包含 | 职责 | 禁止 |
| --- | --- | --- | --- |
| Model（Core） | RunModel、BranchHookModel、只读规则数据、CaptureRecord、FishSummary | 保存本局与能力数据，提供派生计算，变化时发纯数据事件 | 引用 UnityEngine、ScriptableObject、View 或场景对象 |
| 配置资源（Game） | FishingConfig、FishDefinition、BranchHookConfig、AbilityDefinition | 在 Unity 中编辑规则初值与美术引用，由 GameBootstrap 转为规则快照 | 直接作为 Core 规则层的依赖，或运行时写回资产 |
| View | HudView、ResultView、TutorialView、PauseView、FishActor、HookView、CameraRig | 只负责展示与上报用户操作 | 写规则、直接改 Model |
| Controller（Core） | FishingFlowController、BranchHookController、AbilityController | 用纯数据裁决规则、驱动状态切换与本局数据更新 | 调用 Physics2D、Time 或直接操作 UI 与场景组件 |
| Unity 适配层（Game） | GameBootstrap、FishSpawner、InputController、接触检测适配器 | 转换配置、执行输入与物理查询、提交批次、把规则结果应用到场景 | 在碰撞回调里绕过统一裁决直接登记捕获 |
| Services | GameClock、EventBus、ObjectPool、AudioService | 提供时间、事件、池与音频；纯 C# 服务可放 Core，Unity 相关实现放 Game | 让 Core 反向依赖 Game |

数据流固定为一条线：**Unity 输入与检测 → 纯数据输入或接触批次 → Controller 裁决 → 修改 Model → 数据事件 → View 刷新**。例如鱼头只上报接触候选，是否扣保护、是否捕获、是否转上收，都由 FishingFlowController 在批次完整后按当前状态判断，规则不分散在鱼、鱼钩和 UI 脚本里。

**配置与程序集边界**：GameBootstrap 在每局初始化时，将 ScriptableObject 中的规则字段复制为 Core 定义的只读 `FishingRules`、`FishRules`、`BranchHookRules` 与 `AbilityRules`。Core 只接收 ID、枚举、数值等纯数据；预制体、Sprite、AudioClip 等引用留在 Game 层，通过 ID 查找。规则层不直接读取 Unity 的 Time、Physics2D 或随机数 API，时间、接触批次与生成结果由适配层显式提供；Core 的事件载荷也不携带场景组件。

### 6.2 状态机

- 接口 `IState`：`Enter()`、`Tick(dt)`、`Exit()`；每个流程状态一个类。
- FishingFlowController 持有 `Dictionary<RunState, IState>` 与 `ChangeState()`，**只有它能修改 RunModel 的状态字段**。
- 暂停不是状态迁移：用 GameClock 暂停，并记录暂停前状态；恢复时直接继续。
- 每个状态的进入与离开只做三类事：初始化数据、开关表现、订阅或取消订阅事件。

### 6.3 设计模式落点

| 模式 | 落点 | 解决的问题 |
| --- | --- | --- |
| State | 流程状态机 | 避免一个巨大的 Update 里堆分支 |
| Observer | Model 事件、EventBus | View 与规则解耦，HUD 不查场景 |
| Object Pool | 鱼、飘字、气泡、挂鱼特效 | 避免频繁实例化与垃圾回收 |
| Strategy | 输入源（鼠标、触摸、重力）、鱼的游动行为 | 可替换、可扩展 |
| Factory | FishFactory 按 FishDefinition 创建鱼 | 配置驱动，新增鱼种不改代码 |
| ScriptableObject | 全局配置与鱼种配置 | 数据驱动，调参不改代码 |

### 6.4 关键类职责

| 类 | 层 | 职责 |
| --- | --- | --- |
| FishingConfig / FishDefinition | Game 配置资源 | 可在编辑器调参，保存资源引用，不直接传入 Core |
| FishingRules / FishRules / BranchHookRules / AbilityRules | Core 规则数据 | 每局从资产复制的只读纯数据，不包含 Unity 类型 |
| GameBootstrap | Game 适配层 | 装配依赖、转换配置，连接场景与规则层并驱动固定步裁决 |
| RunModel | Model | 本局数据与事件 |
| FishingFlowController | Core Controller | 唯一的规则裁决者：阶段切换、保护、捕获、满载、结算时机；统一提交主钩与分支的成功捕获 |
| BranchHookController | Core Controller | 判断分支展开状态、鱼种资格与剩余容量，参与 3.4 节分配；不持有另一套捕获记录 |

| InputController | Controller | 把鼠标或触摸转成目标横向位置 |
| CameraRig | View | 跟随与上下行偏移 |
| HudView / ResultView / TutorialView / PauseView | View | 展示数据，把按钮操作交给 Controller |

| StartMenuView | View | 起始页：开始游戏、教学、退出，按钮操作交给流程控制器 |

### 6.5 目录与代码规范

```
Assets/_Game/
  Scripts/
    Core/（纯 C#：Model、Rules、States、Controller、Abilities；Core.asmdef）
    Game/（Unity：Configuration、Controller、View、Services、Debug；Game.asmdef）
  Configs/  FishingConfig.asset  Fish_*.asset
  Prefabs/  Art/  Audio/  Scenes/（Main）
```

- Core 与 Game 分成两个程序集定义，依赖方向仅为 Game → Core；Core 禁用 Unity 引用且不引用 Game。ScriptableObject、MonoBehaviour 和所有 Unity 资源类型留在 Game，编辑器测试只需构造纯规则数据与接触批次即可运行 Core。
- 命名：类与方法 PascalCase，私有字段 `_camelCase`，事件以 `On` 开头。
- 注释：所有公开类与方法写 XML `summary`；规则相关代码额外写“为什么这么判”，而不是复述代码。
- 一个脚本只做一件事，超过 300 行就拆。

## 7. 表现与音效需求

表现按层次推进，每一层都能独立交付，时间不够时从最上层砍起。

| 层级 | 内容 | 优先级 |
| --- | --- | --- |
| L0 占位 | 程序化图形或纯色精灵，纯色水体背景；先让整局跑通 | P0 |
| L1 基础 | 鱼的图片、水体渐变背景、两侧岩壁与视差、钩灯三色、冰面场景 | P0 到 P1 |
| L2 反馈 | 捕获缩放与飘字、保护破裂的气泡粒子、鱼尾摆动、满载时的速度线与镜头轻微拉伸 | P1 |
| L3 演出 | 倒计时数字动画、出水弹跳、结算卡片依次翻入、轻微屏幕震动 | P1 到 P2 |
| L4 氛围 | 随深度渐暗、光柱、深处鱼影、背景音乐、各类音效、手机震动 | P2 |

要点：

- 动画使用 DOTween 或自写缓动，不依赖付费插件；所有动画读取 GameClock，暂停时一起停。
- 满载加速要“看得出来”：速度线、背景拉伸、钩灯变红，三者至少做两项。
- 美术采用现有资源或程序化绘制，优先让玩法反馈清楚可读。

## 8. 扩展玩法池（创新点）

### 8.1 选择原则

扩展玩法复用现有鱼种与数据，围绕玩家的选路和收线决策展开，并保持第 3 章的核心规则一致。

### 8.2 候选一览

| 编号 | 名称 | 玩法 | 改变的决策 | 工作量 | 风险 |
| --- | --- | --- | --- | --- | --- |
| E1 | **分散鱼钩** | 上收时展开分支小钩，可钩所有一星鱼，不占主容量 | 往哪片一星鱼群上收；解决“满载后只是等待” | 中 | 判定增多，需控制视觉杂乱 |
| E2 | 下潜声呐 | 下潜时释放，驱散附近小鱼，避免误撞小鱼触发收钩（已确认） | 何时清障，以及是否牺牲小鱼分布 | 小 | 需要小鱼的受惊状态与逃离行为 |
| E3 | 磁吸 | 上收期限时放大鱼头判定半径或轻微牵引鱼 | 是否为稀有鱼冒险偏离 | 小 | 数值易失衡 |
| E4 | 气泡补给 | 下潜路线上出现补给泡，吃到恢复 1 次保护 | 是否为补给偏离路线 | 小 | 几乎无 |
| E5 | 洋流区 | 某深度段有横向水流，推着鱼钩漂移 | 提前抵抗还是顺流 | 小到中 | 手感需调 |
| E6 | 危险鱼（水母） | 触碰会甩掉最近一条已抓的鱼，保护可抵消 | 上收也要避障，不再是纯收割 | 中 | 容易让人觉得不公平 |
| E7 | 影子鱼 | 深处只见鱼影，靠近后现身并加速逃跑，是稀有鱼 | 是否追击稀有鱼 | 中 | 需要鱼行为状态 |
| E8 | 同类连击 | 连续抓同一种鱼，结算价值逐级加成 | 抓取顺序 | 小 | 钩上挂鱼难控制顺序，加成偏弱 |
| E9 | 深渊赌注 | 到底后可选“再下 30 米”，保护失效、鱼更密、稀有度更高 | 见好就收还是冒险 | 中 | 需要额外一段地图 |
| E10 | 重力感应 / 每日种子 | 可选的重力操控；固定种子的每日挑战 | 操作方式与重复游玩 | 小 | 调试与测试成本 |

### 8.3 推荐组合

**主推 E1 分散鱼钩，再配 E2 下潜声呐（已确认）；两项能力放在同一套“能力”框架下，分管上收与下潜。**

理由：

1. 录屏里满载之后只剩约 2 秒的快速回收，玩家基本无事可做；分支钩让“满载后”也有事做，这是对原玩法的真实补强。
2. 分钩复用鱼种配置的星级，声呐继续使用“是否小鱼”字段，不需要新美术、新鱼种。
3. 它能展示架构的可扩展性：能力各自实现资格、次数与效果，接入统一的候选裁决和捕获提交；分支优先分配属于核心捕获流程需要明确支持的扩展。
4. 声呐管下潜、分支钩管上收，整局都有主动操作，而不是只有躲与收；两者同属“能力”框架，也证明它不是为分支钩写的特例。

### 8.4 E1 分散鱼钩：详细设计

**一句话**：上收拾取淡金宝物后，主钩两侧展开分支小钩，随主钩一起上升；分支钩可钩所有一星鱼，捕获不占主容量。

#### 8.4.1 规则

| 编号 | 规则 |
| --- | --- |
| B1 | 仅在 Ascending 状态可用，满载前后都可用；每局可用 1 次（配置）；下潜期不可用，避免过强 |
| B2 | 触发后在主钩两侧弹出 2 个分支钩（配置），以扇形散开到设定半径，之后跟随主钩上升，保持相对偏移并带轻微弹性延迟 |
| B3 | 分支钩捕获所有一星且可捕获的鱼，不区分体型；遇到二星及以上鱼默认直接穿过 |
| B4 | 每个分支钩容量 3，分支总容量 6，**不占主容量 10**，也不参与满载判定 |
| B5 | 主钩满载后分支钩继续工作直到出水；满载加速时用扫掠检测，避免高速漏判 |
| B6 | 同一物理步内，同一条一星鱼同时成为主钩与分支钩候选时，**有余量的分支钩优先**；多个分支按距离、鱼实例 ID、钩 ID 稳定排序。分支均满或无资格时，主钩仍可按余量捕获；分配不依赖回调顺序，见 3.4 节 |
| B7 | 分支鱼与主钩鱼同样按价值计入收益。每鱼种合并一张卡，显示总数量及“主钩 ×N / 分支 ×M”；分支数量大于 0 才标“含分支”。全部记录求和得到两种货币总额 |
| B8 | 可选风险规则（默认关，保留 breakOnLarge 字段名）：分支钩被二星及以上鱼碰到则该分支收回，已挂的鱼保留，但不再继续捕获；一星鱼不触发此风险 |

B6 让分支承担一星鱼的捕获，把主钩容量留给更高星鱼；展开时机沿用当前的宝物拾取规则。

#### 8.4.2 参数（BranchHookConfig）

| 参数 | 初值 |
| --- | --- |
| 分支钩数量 | 2 |
| 每钩容量 | 3 |
| 展开半径 | 约 0.18 倍屏宽 |
| 展开时间 | 0.25 秒 |
| 跟随弹性 | 弹簧跟随，阻尼可调 |
| 每局可用次数 | 1 |
| 高星接触收回开关（旧名 breakOnLarge） | 关 |

#### 8.4.3 架构落点

- 新增 `BranchHookConfig`（Game 配置资源）、`BranchHookRules`（Core 只读规则）、`BranchHookModel`（纯 C#，保存展开状态与容量）、`BranchHookController`、`BranchHookView`（复用鱼钩接触上报）。每钩已用数量读取 RunModel 中对应来源钩的捕获记录。
- 接触候选携带来源钩 ID（主钩、分支 A、分支 B），统一进入本物理步缓冲区。FishingFlowController 按 3.4 节先请求 BranchHookController 判断与分配，再分配主钩，最后统一登记成功捕获。**核心捕获流程增加批次分配，基础保护与单钩规则保持原有职责。**
- RunModel 是捕获记录的唯一来源，记录包含 Main / Branch 与具体钩 ID。结算按鱼种合并并保留来源明细，主钩数量、分支数量、总数量与收益均由同一批记录统计。
- HUD 保留“分支 x/6”；沿用 FR-27 修订后的上收宝物接触自动展开，不恢复旧技能按钮。
- 出水演出：分支鱼与主钩鱼一起弹出，分支鱼延后 0.3 秒。
- 分支钩视图走对象池。

#### 8.4.4 验收标准

1. 主钩 10/10 之后，分支钩仍能继续抓到一星鱼，且主容量不变。
2. 基础版下，二星及以上鱼不会被分支钩捕获，也不触发任何效果；一星鱼无论体型均可捕获。
3. 主钩与分支容量均不超限，同一条鱼最多捕获一次。对同一批次分别提交“主钩先报告”“分支先报告”和混合顺序，分配结果一致；两分支同时接触、一个分支已满及全部分支已满的情况均符合 B6。
4. 结算：所有卡片总数量之和＝主钩数＋分支数＝记录条数，金币与贝壳总额正确。同鱼种混合来源只建一张卡并显示来源明细；纯主钩卡无角标，有分支记录才显示“含分支”。
5. 暂停、重开后无残留分支钩与事件订阅。
6. 固定种子下，满载高速段穿过小鱼群，分支钩不漏判。

### 8.5 通用“能力”框架

为了让分支钩不是特例，把它放进一个通用的能力框架里：

- `IAbility` 定义于 Core：`CanActivate(RunModel)`、`Activate()`、`Tick(dt)`、`Cancel()`；`AbilityDefinition` 是 Game 层的 ScriptableObject，记录图标、名称、次数或冷却、允许使用的状态，初始化时转换为 Core 的 `AbilityRules`，图标引用不进入规则层。
- `AbilityController` 管理能力槽，每局 2 个槽：下潜期的声呐、上收期的分支钩，各有独立按钮，无需开局选择。
- 用到的模式：Strategy（每个能力是一种策略）与 Command（激活是一次可撤销的命令）。
- 能力的激活与结束通过事件通知 HUD 与音频。

#### 8.5.1 下潜声呐（E2 改版，已确认）

**一句话**：下潜时点声呐按钮，发出一圈声波把附近的小鱼驱散，避免误撞小鱼触发收钩。保护次数是被动容错，声呐是主动清障，两者互补，不重叠。

| 编号 | 规则 |
| --- | --- |
| S1 | 仅在 Diving 状态可用（不含底部区与上收期）；每局 2 次，冷却 4 秒，均可配置 |
| S2 | 释放后以鱼钩为中心发出声波环，0.4 秒内扩展到作用半径（初值 4 米） |
| S3 | 声波只影响“小鱼”（小红鱼、小银鱼）：范围内的小鱼进入“受惊”状态，沿远离鱼钩的方向横向加速逃离，2.5 秒后恢复正常游动，不瞬移回原位 |
| S4 | 受惊期内，小鱼的鱼头判定区关闭：与鱼钩重叠既不扣保护，也不触发收钩，也不能被捕获；恢复后判定区重新开启 |
| S5 | 河豚、蓝纹鱼、红鱼、蝴蝶鱼、鳗鱼不受声呐影响，仍需手动避让；声呐只解决小鱼群，不解决全部障碍 |
| S6 | 声呐不消耗保护，也不替代保护：误撞大鱼或声波没覆盖到的小鱼，仍按 R2 处理 |
| S7 | 被驱散的小鱼可能离开上收路线，会减少分散鱼钩的收获；是否动用声呐，是玩家要权衡的取舍 |

| 参数 | 初值 |
| --- | --- |
| 每局次数 | 2 |
| 冷却 | 4 秒 |
| 作用半径 | 4 米 |
| 声波展开时间 | 0.4 秒 |
| 受惊时长 | 2.5 秒 |
| 逃离速度 | 该鱼游速的 3 倍 |

**实现要点**

- `SonarAbility` 实现 `IAbility`，由 `AbilityController` 管理次数、冷却与状态限制；按钮放在侧边拇指区，显示剩余次数。
- 声波的空间查询由 Game 适配层执行，以鱼钩为圆心，只查“小鱼”图层；将命中鱼的 ID 与所需纯数值提交给 Core 的 SonarAbility，裁决后由 Game 层对相应 FishActor 应用 `Scare(逃离方向, 时长)`。Physics2D、Collider 与 FishActor 引用不进入 Core。
- `FishActor` 增加 Swimming 与 Scared 两个小状态（State 模式）；受惊时关闭判定区，计时读取 GameClock，暂停时一起停。
- 发布 `SonarFired` 事件，表现层播放声波环与音效，规则层不关心表现。

**验收标准**

1. 释放后，范围内的小鱼被驱散；受惊期内与鱼钩重叠，不扣保护、不触发收钩。
2. 大鱼不受影响，接触时仍按 R2 处理。
3. 次数与冷却正确；底部区与上收期按钮不可用；暂停时冷却不走。
4. 受惊期结束后，小鱼恢复游动与判定，上收时可正常被捕获。
5. 重开后次数重置，场景中无残留的受惊鱼。

### 8.6 平衡与风险

| 风险 | 对策 |
| --- | --- |
| 分支钩过强 | 独立总容量仍为 6；改为所有一星鱼后，不再沿用“仅小鱼、最多约 +30 金币”的旧估算，实际收益平衡待实操 |
| 判定数量增加导致性能下降 | 分支回调覆盖 Default／小鱼层，候选过滤 FishActor，复用原查询缓冲和有限鱼群；设备性能另验收 |
| 画面杂乱 | 分支钩缩小，用半透明细线连接，颜色与主钩区分 |
| 手机误触 | 技能按钮放在侧边拇指区，不压拖动区，带防抖 |
| 规则回归 | 对分支规则（容量、去重、优先分配）写编辑器单元测试 |
| 声呐让下潜过于轻松 | 只影响小鱼，河豚等大鱼仍需手动避让；每局 2 次加 4 秒冷却 |
| 声呐暂时影响部分一星鱼的位置 | 小鱼受惊 2.5 秒后恢复游动；蓝纹鱼、河豚不受声呐驱散影响，仍可被分钩捕获 |

**已确认的决策**

1. 横向操作默认**相对拖动**，保留“跟随触点”作为备选。
2. 创新点定为**分散鱼钩**（上收期）加**下潜声呐**（下潜期）。
3. 做一个简单**起始页**（FR-17）。
4. 无硬性截止日期，目标**一周内**完成，按第 9 章的 7 天排期执行。
5. 保护按接触进入判定：持续重叠只扣一次，无敌到期不补判，完全分离再接触才重新判断；底部区与上收不延续保护无敌。
6. 主钩与分支分别计数、共用唯一捕获记录；结算按鱼种合并，保留来源明细，总收益覆盖两者。
7. 多钩按物理步统一裁决，同一步先分支后主钩，稳定排序与统一提交，结果不依赖回调顺序。
